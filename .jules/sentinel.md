## 2026-09-21 - [Hardcoded Database Credentials in Orchestration Files]
**Vulnerability:** Found hardcoded database credentials (`crm_password`, `crm_user`) in plain text inside `docker-compose.yml`. This exposes sensitive connection details directly in version control.
**Learning:** Even though `docker-compose.yml` is often used for local development, hardcoding credentials in version-controlled infrastructure/orchestration files is a critical anti-pattern that can leak into production environments or expose local data to anyone with repo access.
**Prevention:** Use environment variables with default fallbacks (e.g., `${POSTGRES_PASSWORD:-default_pass}`) in `docker-compose.yml` and provide a `.env.example` file. Never commit `.env` files containing actual secrets.## 2024-05-18 - [Insecure Direct Object Reference (IDOR) via Client-Provided tenantId]
**Vulnerability:** Found that the GraphQL `createJob` mutation in `shared/contracts/schema.graphql` accepted `tenantId` directly from the client. This allows malicious actors to potentially create or modify records across different tenants by providing an arbitrary UUID, leading to severe data isolation bypass.
**Learning:** In a multi-tenant architecture, sensitive context like `tenantId` must never be trusted from client payloads. It should be securely inferred server-side from the authenticated user's session or token (e.g., JWT).
**Prevention:** Remove `tenantId` from all API contract inputs. Enforce tenant isolation strictly at the resolver/controller level by injecting context from authenticated headers.
